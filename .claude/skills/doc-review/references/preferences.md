# Josh's doc-review preferences

Append a dated entry under "Learned in use" every time he corrects how a review
was done. Keep entries general: this skill is for any document, and the repo is
public. No project details, domain terms, or names.

## Learned in use

- **2026-10-02 — Unaddressed means not yet, not no.** "Wherever I didn't address a
  comment assume I haven't gotten to it not that I disagreed with it." Carry it
  forward, marked *(earlier)*.
- **2026-10-02 — Remove what's done.** As he resolves items, delete them from the
  feedback file and renumber. No "already resolved" section.
- **2026-10-02 — Just fix trivial edits.** A missing comma got: "For things like
  that, it's easier if you just make the change and tell me."
- **2026-10-02 — Give exact before/after text.** "What specific change do I make?
  What text do I have now, what text should it be?" A vague "fix this section"
  item costs him a round trip.
- **2026-10-02 — Check the doc's structure before calling something missing.** I
  asked him to add content to one section that another section already included
  by reference ("same as X").
- **2026-10-02 — Don't propose options a requirement rules out.** I offered an
  alternative the doc's stated requirements had already excluded.
- **2026-10-02 — Match the doc's level of detail.** An implementation step any
  engineer would do anyway was "obvious to whoever needs to implement it."
- **2026-10-02 — An owner's reply settles it.** When the person who owns the
  decision has answered in a comment, that stands; don't push to close or reword it.
- **2026-10-02 — Respect the precedence rule he sets** for conflicting sources,
  unless the decision owner has ruled otherwise on that specific point.
- **2026-10-02 — One item per table row.** Never combine two things in one row; each
  gets its own entry.
- **2026-10-02 — Match the surrounding entries.** A new entry in a list or table
  should be the same length and level as the ones beside it.
- **2026-10-02 — Don't give a process agency.** I wrote that a transformation step
  should "decide" something. "Transformation shouldn't 'decide' anything." When a
  step lacks a rule, name the missing rule and who owns it.
- **2026-10-02 — Say what happens, not every step.** A step-by-step list of data
  transformations was "way too low level for this document. Just knowing that we're
  taking the data and prepping it is enough."
- **2026-10-02 — Don't overstate a constraint.** I claimed a stored document "can't
  hold a foreign key." It can hold the ID as an unenforced reference. Say what the
  limitation actually is, or drop the point.
- **2026-10-02 — The author decides what's worth detailing.** He mentioned supporting
  tables briefly and "elected not to go into further detail." Once a gap is
  acknowledged in the doc, don't push for more depth.
- **2026-10-02 — Formatting matters to him, capitalization included.** Every edit must
  leave identifiers, casing, and punctuation exactly right. Docs auto-capitalizes the
  first word of a cell and italicizes text between underscores; check each edit with a
  zoom and undo those changes immediately (see google-docs-mechanics.md).
- **2026-10-02 — Don't raise items that depend on an unmade decision.** I asked how a
  process would detect a change, which only matters if that process runs automatically.
  It didn't, so the item was moot. Check the assumption an item rests on before raising it.
- **2026-10-02 — Give a core requirement its own sentence.** I buried "the runner
  never regenerates inputs itself" after a semicolon. He promoted it to its own
  sentence (and bolded it) because it's a core requirement. Use "must" for
  obligations, and don't tuck a key rule into a subordinate clause. This isn't a
  ban on semicolons.
- **2026-10-02 — Counted lists are numbered.** When the lead-in states a count ("it does
  three things:"), the list that follows is numbered, not bulleted.
